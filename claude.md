# Claude.md - SDR Module Project Guide

## Project Overview

SDR Module is a Software Defined Radio framework for dual-SDR operation using RTL-SDR and HackRF One devices. It provides signal analysis, visualization, classification, and protocol decoding capabilities for amateur radio operators and signal analysts.

Most features are used through the PyQt6 GUI (`python -m sdr_module.gui`): spectrum and waterfall, a receiver with audio (broadcast FM in stereo), live decoders, recording and playback, a scanner, signal identification, a second receiver window, and transmitting on a HackRF One with license and power checks. The `sdr-scan` CLI covers scanning (with one SDR, or two at once: `sdr-scan scan --dual`), decoding, encoding and CHIRP channel files. The demo device simulates signals (including decodable traffic), so receiving, decoding, recording, scanning and the signal tools work without hardware; transmitting needs a HackRF One, and each device's own gain and front-end settings need that device.

**Version**: 0.2.0 (Beta)
**Python**: 3.10 - 3.14
**License**: MIT

## Coding Standards

### Formatting
- **Black**: 88 character line length
- **isort**: Black-compatible import sorting
- **Type hints**: Required for new code; mypy checks everything except `gui/` and `ham/gui/`, whose errors `pyproject.toml` ignores

### Naming Conventions
- Classes: `PascalCase` (e.g., `DualSDRController`, `SpectrumAnalyzer`)
- Functions/methods: `snake_case` (e.g., `set_frequency`, `demodulate`)
- Constants: `UPPER_SNAKE_CASE`
- Private members: Leading underscore (e.g., `_state`, `_lock`)

### Architecture Patterns

1. **Abstract Base Classes** - Used for device, demodulator, and protocol interfaces
2. **Dataclasses** - Used for configuration and state objects (often immutable)
3. **Enums** - Extensive use for type-safe constants (OperationMode, ModulationType, etc.)
4. **Thread Safety** - RLock used for shared state; thread-safety documented in docstrings
5. **Qt-free logic** - What the GUI computes lives in modules without Qt where it can (`dsp/`, `core/`, and `gui/tuning.py`, `audio_chain.py`, `stereo_audio.py`, `deemphasis.py`, `playback_sound.py`, `scan_engine.py`, `device_settings.py`, `plot_view.py`, `plot_readout.py`, `rds_station.py`, `decoder_spool.py`, `frame_pipeline.py`, and all but the Qt mixins of `second_receiver_audio.py` and `second_receiver_decoding.py`), so it is tested a block at a time without a window. Panels show state and emit signals; the window, or a host object such as `WindowScannerHost`, acts on them.

### Documentation
- Module docstrings describing purpose
- Function docstrings with Args, Returns, and Raises sections
- Thread-safety notes on critical classes

## Key Modules

### Core (`core/`)
- `band_info.py` - The band plan line at a frequency (Info tab, FREQ tooltip)
- `band_plan.py` - Which band a frequency is in and how it is usually listened to (CW in the CW/data segments of the amateur SSB bands, USB on the FT8/FT4 channels); `KHZ_BELOW_HZ`: frequencies below 2 MHz are named in kHz. A preset's FM deviation comes from its `fm_deviation` (`FrequencyPreset`: the pagers' "12.5 kHz", their ±4.5–4.8 kHz swing clipped at 5 kHz), else from its channel width (`preset_listening`); the control panel's Apply Preset and the Decoder's `PROTOCOL_TUNE` agree with it
- `chirp_csv.py` - CHIRP-compatible CSV import/export for saved channels
- `config.py` - Configuration management with validation
- `device_manager.py` - Device enumeration and lifecycle management
- `dual_sdr.py` - Dual-SDR controller (modes: see Hardware Support)
- `wideband_scan.py` - `WidebandScan`: one or two open devices sweep one range at once, each in a thread of its own (a step: tune, drop what was queued, let the tuner settle, measure), sharing the range through `dsp/sweep.py`'s `SharedSweep`; the signals are merged in frequency order, each once (`SignalList`: a station both saw keeps its stronger reading). A page one device can't measure (it refused the frequency, returned no samples or raised) goes to the other; a device that fails `MAX_FAILURES` pages in a row is left out of the rest of that pass (and tried again in the next). Callbacks run one at a time in the scan's thread. Used by `DualSDRController.start_wideband_scan` and `sdr-scan scan --dual`
- `frequency_manager.py` - TX lockouts, license profiles, band privileges, RX presets (`RX_PRESETS`; a preset can name the decoder it turns on, and the window turns that decoder off again once you tune away from where it is heard: `_release_preset_decoder`)
- `sample_buffer.py` - Thread-safe circular sample buffers

### DSP (`dsp/`)
- `spectrum.py` - FFT-based spectrum analyzer
- `frame_spectrum.py` - Spectrum of a whole display frame (mean for the spectrum, max for the waterfall; a frame longer than `max_samples` in evenly spread segments), FFT sizes and windows
- `demodulators.py` - AM, FM, SSB, CW, OOK, FSK, PSK, GFSK, MSK, QAM
- `filters.py` - FIR filters, resamplers, AGC, squelch, CTCSS detection, noise reduction (a `Squelch` given `SquelchConfig(mode=SquelchMode.DCS)` still raises `NotImplementedError`: DCS is `dcs.py`'s `DcsDetector`). `CTCSSDetector` lets a held tone go at a reverse burst (the tone's phase turned as the user stops talking: 180 degrees for about 150 ms on most radios, 120 for about 180 ms on Motorola's; any turn over 90 degrees is heard; `CTCSSDetector(reverse_burst=True)`, settable while it runs: Radio > Audio > Squelch Tail Elimination), and `ctcss_transmission` sends a tone ending in one (tests; the demo's 2 m repeater builds its own burst from `CTCSS_BURST_DEG` and `CTCSS_BURST_S`)
- `audio_filters.py` - Listening filters for demodulated audio, streaming (any block sizes give the same audio) and NumPy only: `SosFilter` (biquads in SciPy's `sos` layout, without SciPy), `AudioNotch` (`"off"`, `"auto"`: up to three steady whistles its `ToneFinder` hears, `MAX_TONES`, each with a notch of its own, the strongest first and each followed as it drifts; a fourth takes the weakest one's notch only when 6 dB (`REPLACE_DB`) stronger, and two closer than `APART_BINS` bins of its spectrum, about 23 Hz at 48 kHz, count as one; or `"manual"`: one frequency) and `LowCut` (an inverse-Chebyshev high-pass); every notch and the low cut engage, move and let go without a click
- `dcs.py` - DCS (digital-coded squelch): the 104 standard codes, an encoder (`dcs_waveform`: tests and the demo device), `format_dcs` / `parse_dcs` (`"D023N"`), `dcs_label` (`"DCS 023 N"`), `dcs_same_signal` (a code's twin of the other polarity sends the same bits: 023 N and 047 I) and `DcsDetector`, fed FM discriminator audio before any DC blocking. The turn-off code that ends a DCS transmission (`DCS_TURN_OFF_HZ`, 134.4 Hz for `DCS_TURN_OFF_S`; `dcs_turn_off`, `dcs_transmission` send it) makes `DcsDetector` let a held code go at once (`turned_off`), whatever Squelch Tail Elimination says
- `nco.py`, `channelizer.py` - Streaming frequency shift and decimation: a channel out of the span
- `live_decoders.py` - Live decoders on raw I/Q (`LIVE_DECODERS`: POCSAG, FLEX, AX.25/APRS, ADS-B, ACARS, RDS, CW); `create_live_decoder(..., recording=True)` is for a recording playing: a rate too low for the protocol is then named as the recording's ("this recording is 1 MS/s"), with no advice to change the sample rate, which a recording can't; `create_live_decoder(..., audio=True)` decodes a receiver's audio instead of I/Q (an audio recording's own samples): APRS, POCSAG and FLEX after the FM discriminator, ACARS after the AM detector (`audio_input(name)` says which; the others have no audio entry). `describe_message` gives a FLEX page's address with its phase and speed ("1000999 (D, 6400 bps)"), as the Decoder's table, details card and Export show it. ADS-B's `skipped_per_s` (the replies a busy sky left unread, reading 0 until they have gone unread for `SKIPPED_SETTLE_S` at `SKIPPED_MIN_PER_S` or more a second) and `skipped_text` / `skipped_tip` are the busy-sky line both windows show
- `protocols.py` - Protocol decoders (POCSAG, AX.25/APRS, RDS, ADS-B, FLEX, ACARS), bit slicer, BCH, APRS parsing. `FLEXDecoder` reads 1600, 3200 and 6400 bps frames in every phase (`FLEXMessage.baud_rate`, `phase`; a 3200-symbol/s frame needs 9.6 kS/s or more, else it is counted as unsupported), following the input's DC between frames and holding it through each one; below 2.5 MS/s `ADSBDecoder` reads Mode S through `mode_s.py`
- `mode_s.py` - `ModeSDemodulator`: Mode S replies at 2.0 to 2.5 MS/s, where a sample spans most of a chip: each reply's start time, pulse level and noise fitted from its preamble, its bits read at that time or, for a reply that then fails its check, found by a Viterbi search. The fits and searches have a budget per second of signal (`FITS_PER_S`, `SEARCHES_PER_S`): over it the clearest preambles are read first and the rest counted in `skipped` (said as "Busy sky: about 870 replies a second weren't read ..." in the Decoder tab and once in the status bar; Decode Recording's summary gives the count instead: "1,905 replies weren't read: too many at once for 2.4 MS/s ...")
- `protocol_encoders.py` - POCSAG, FLEX (every speed: `FLEX_SPEEDS`, `flex_baseband(..., speed=)`), AX.25/APRS, ACARS, Morse and RDS transmitters (tests and the demo device; there is no ADS-B encoder, the demo builds its Mode S frames in `device_dialog.py`)
- `rds.py`, `morse.py`, `stereo_pilot.py` - RDS physical layer, streaming Morse decoder, 19 kHz pilot detector. A word that is one E or one T is what a crash of static keys, so `MorseDecoder` shows one beside longer words (or in a line of such words) only when it was keyed like code: steady marks (`KeyingDetector.steady`) at the speed already established, and a word gap from that code before or after it (the `KEYED_*` settings; one alone between two pauses still isn't shown, and code sent letter by letter shows them as before); a caller of `process(keying)` that passes no `steady` never has one counted as keyed (lone letters behave as before). `PitchFinder` finds a Morse tone's pitch in audio (the averaged spectrum's peak between 150 Hz and 3 kHz: `sdr-scan decode cw` of an audio recording)
- `fm_stereo.py` - `StereoDecoder`: broadcast FM's stereo difference signal from the multiplex (the 19 kHz pilot followed, L-R taken off its 38 kHz subcarrier) and how much of it to play: the blend keeps stereo's hiss 50 dB below full scale (`FULL_SNR_DB`), goes to mono below 30 dB (`MONO_SNR_DB`) and without a pilot, falls at once and widens back over `RISE_S`. Its de-emphasis `tau_s` (75 or 50 µs) and `blending` (Radio > Audio > Stereo Blend: `BLEND_OFFSETS_DB` moves both thresholds 6 dB down for Less, up for More; `full_snr_db`, `mono_snr_db`) are settable while it runs and glide over 20 ms
- `classifiers.py`, `signal_id.py` - Signal classification with confidence; identifying the tuned signal and how to listen to it (Signal tab > Identify). The FM deviation it suggests must hold the station's swing, or Apply Mode leads straight to "FM audio is clipping" (shown when more than 5 % of the audio is beyond the deviation), and be no wider, or the station is heard quieter (`listening_for` keeps the band plan's deviation where that holds the swing and the peak is at least a quarter of it): `_swing_to_hold` takes the larger of the peak (`freq_peak_hz`, the swing exceeded 0.5 % of the time) and, with 10 % to spare, the swing exceeded 5 % of the time (`freq_p95_hz`). Voice reaches its peak only now and then, so it is held at its peak (a 2 m station limited at ±5 kHz gets 5 kHz); a tone stays near its peak and keeps the margin. How far a spectrum bin stands above the noise is judged against the noise's measured spread (`_spread` in `_spectrum_features`), not the spread independent averages would have: neighbouring bins of a windowed spectrum aren't independent and the demo's noise is rougher than white, so otherwise the noise's ripple counts as signal all over a wide capture (Identify in broadcast FM looks 800 kHz wide) and joins a call to a station hundreds of kHz away. An AM station is as wide as its sidebands reach (`sideband_edge_hz`), judged with the spectrum mirrored about the carrier (the sidebands are alike either side, the noise isn't). `SignalIdentifier(..., channel_pass_hz=, analysis_rate=)` takes a receiver's channel as it is and judges it at the rate its own filter would have given (see `signal_tools.py`)
- `signal_list.py`, `bursts.py` - Signals in a spectrum or a recording; bursts and rtl_433-style pulse analysis
- `afc.py` - Signal tracking (Radio > Track Signal (AFC))
- `sweep.py` - Sweep planning and measurement (Scanner tab, `sdr-scan scan`); `SharedSweep` shares one sweep between two receivers (`SweepReceiver`: a sample rate and a tuning range): each first takes what only it tunes, then they meet from opposite ends, each page sized for its own rate (the wideband scan, the Scanner tab's Use both receivers); `scanner.py` is the older library scanner
- `recording.py` - I/Q recording/playback (raw cu8/cs8/cs16/cf32/cf64, WAV, SigMF), `.sigmf-meta` sidecars, format guessing; WAV goes through `wav_file.py` (`IQRecorder.start` with `expected_samples` that fit writes a classic file; without them, a file that turns into RF64 if it grows past 4 GiB; `IQPlayer`, `AudioPlayer` and `FormatDetector` read classic WAV, RF64, BW64 and Wave64 through `read_wav_header`, never the `wave` module). WAV I/Q is read in 8-, 16-, 24- and 32-bit integers and 32- and 64-bit floating point, every sample at full scale 1.0 (`wav_values`; `IQPlayer.wav_header` and `FormatInfo.metadata["wav_sample_type"]` say how it is stored, `sample_format` what it is read as: cf32 for 24 and 32 bits). A one-channel WAV file is read as I/Q through `real_iq.py` (see Important Notes); `wav_frames` gives its own samples, a chunk at a time, for decoding its sound as audio. A file of more than two channels raises `WavError`. Writing WAV is as before: Save Recording and Convert Recording write 16-bit (or 8-bit) integer I/Q
- `wav_file.py` - WAV files of any size (standard library only): `WavWriter` writes integer PCM, a classic file while it fits and RF64 past 4 GiB, in place (a size known to fit gets the classic 44-byte header, any other an 80-byte header whose JUNK chunk becomes RF64's ds64), the header up to date after every write; `read_wav_header` reads classic, RF64, BW64 and Wave64 files and counts one cut short or never finished as what it holds. It reads the samples `READ_WIDTHS` lists (`WavHeader.sample_type` "int" or "float", `sample_name` "24-bit integer"); 24-bit samples in 32-bit words (as ALSA's `arecord -f S24_LE` wrote them), whose header doesn't say where in each word a sample lies, are read where a look at the data shows them (`WavHeader.justified`, "left" or "right", `bits` 24), and words that fit neither layout, 64-bit integers, 16-bit floats and compressed formats are refused saying what they are; `WavError` is both a `ValueError` and a `wave.Error`. Given an open file, it leaves it where the samples start
- `real_iq.py` - One-channel (real) recordings as I/Q (NumPy only): `real_to_iq` makes the analytic signal at half the file's rate, centered on a quarter of it (`iq_rate`, `iq_center`, `iq_count`), so the plots show the file's own frequencies (0 Hz to half its rate) once each, not mirrored; the Hilbert filter is sized by rate (`context_for`: 34 taps at high rates, 212 at 48 kHz, within `WORK_PER_S`), and a stretch of I/Q depends only on the samples around it, so seeking needs no history. `AUDIO_RATE_MAX` (200 kHz) and `is_audio(frame_rate, center_hz)`: the one rule for whether such a file is a receiver's sound (an audio rate, at its own frequencies, not placed elsewhere by its metadata), which the window and `sdr-scan decode` both follow
- `time_stretch.py` - `TimeStretch`: streaming WSOLA, audio played faster or slower with its pitch kept (25 ms frames, `FRAME_S`, each moved up to `SEARCH_S` to where it best continues the last), mono or `(n, 2)` (both sides take each frame from the same place, lined up on both sides' correlations, so opposite-polarity channels stay clean); any block sizes give the same output; `feed`, `pull(count, ratio)`, `finish`, `drain`; `time_stretch()` for a whole signal
- `background_writer.py` - `BackgroundWriter`: blocks written in order on a thread of their own from a queue of at most `max_bytes`; `put()` copies the block, or returns False when there is no room (the caller counts it as lost and says so); the first write error stops it and waits in `error` for the caller's thread; `flush()`, `close()`, `abort()`

### GUI (`gui/`)

## Testing

Tests use pytest (about 215 modules): DSP, drivers against fake backends, the CLI, and GUI tests that build the real main window. The suite is large; run the modules for the code you change.

```bash
# GUI tests need no display (CI sets this for every run; some
# GUI test modules don't set it themselves)
export QT_QPA_PLATFORM=offscreen

# Run all tests
pytest

# Run specific test file, or matching tests
pytest tests/test_gui_tuning.py
pytest tests/test_gui_scanner.py -k bookmark

# Fail instead of skipping the GUI tests when PyQt6 is missing (as CI does)
SDR_REQUIRE_GUI=1 pytest tests/test_gui_chrome.py

# The antenna-array package's own tests (plain `pytest` runs tests/ only;
# CI runs these separately)
pytest packages/sdr-antenna-array/tests
```

- **`tests/conftest.py`**: an exception raised in a Qt slot or event handler would make PyQt abort the whole run ("Fatal Python error: Aborted", output lost); the conftest records it instead, and the test it happened in fails with the traceback (`tests/test_qt_callback_errors.py` checks this). It also runs pending `deleteLater()` deletions after each test, closes windows a module leaves open, restores the theme, and points the file dialogs' Documents and Pictures folders at temporary ones. Keys are not reset between tests: a `QTest` click with a modifier leaves the key down for the whole app (a later test's `selectRow` then extends the selection), so release it (`QTest.keyRelease(widget, Qt.Key.Key_Shift)` after a Shift+click, as the radio tuner's seek tests do).
- **Window tests** mostly build on `_WindowTestCase` (`tests/test_gui_chrome.py`): a real `SDRMainWindow` with in-memory settings (`_FakeSettings` in place of `GuiSettings`) and its timers stopped, so a test runs frames by calling `_update_display()`; `demo = True` starts the demo device. Code that creates `GuiSettings()` itself uses the real settings file (`~/.config/SDR Module Team/SDR Module.conf` on Linux); set `XDG_CONFIG_HOME` to a scratch folder to keep a run away from your own. On broadcast FM both windows' speakers get `(n, 2)` blocks (Radio > Audio > Stereo and the Second Receiver's own Stereo switch are on by default), so a fake sink that collects them must take both shapes (as `_FakeSink` in `tests/test_gui_second_receiver.py` does). `_SecondCase` (same module) opens the Second Receiver as Device > Second Receiver... does, `win._second_rx.show()`: only the window its host holds hears from the main window afterwards (a change to Radio > Audio's shared settings, its Listen muting the main window); one built directly, `SecondReceiverWindow(win)`, takes the shared settings only as it opens.

## Hardware Support

- **RTL-SDR**: 500 kHz - 1.766 GHz (below 24 MHz through direct sampling), RX only, 1.0 - 2.56 MS/s in the GUI
- **HackRF One**: 1 MHz - 6 GHz, TX/RX (half duplex), 2 - 20 MS/s. Its firmware switches the RF amp and antenna power off whenever it stops; the driver sends the amp setting again before every RX or TX stream, powers the antenna port (bias tee) again for each reception, and switches it off before transmitting (never powered on the air).
- **Demo device**: simulated signals, 1 - 3.2 MS/s, can't transmit

Dual-SDR operation modes (`core/dual_sdr.py`; `OperationMode.implemented`, `DualSDRController.supported_modes()`):

| Mode | What it does | `DualSDRController` | In the GUI |
| --- | --- | --- | --- |
| `DUAL_RX` | Two receivers on two frequencies | Implemented | Device > Second Receiver... with any free RTL-SDR, HackRF One or a second demo device |
| `FULL_DUPLEX` | RTL-SDR RX + HackRF TX | Implemented | The second receiver keeps receiving while the main window's HackRF transmits |
| `TX_MONITOR` | Monitor own transmission quality | Implemented (attenuate the receiver) | Second receiver's Transmit monitor group: Monitor TX, Follow transmissions |
| `WIDEBAND_SCAN` | Both devices sweep one range at once, each its own part | Implemented: `start_wideband_scan()` / `stop_wideband_scan()` (`core/wideband_scan.py`); `sdr-scan scan --dual` | Scanner tab > Use both receivers (Sweep once or continuously, with Device > Second Receiver... running) |
| `RELAY` | Receive-and-retransmit | Deliberately not implemented: `set_mode` raises `NotImplementedError` saying why (retransmitting what you receive is restricted almost everywhere, e.g. FCC 97.113) | No |

`DualSDRController.use_devices(rtlsdr, hackrf)` takes devices that are already open (two `PolledDevice(MockDevice(), ...)` try dual receive and the wideband scan without hardware). While a wideband scan runs the devices are its own: the other modes, `set_mode`, `use_devices` and `set_rtlsdr_frequency` / `set_hackrf_frequency` are refused (with the reason in the log), and `stop_all()` stops the scan first. Two devices at most, each at its own sample rate and gain (`start_wideband_scan` keeps what each is set to; `sdr-scan scan --dual` takes one `--rate` or two, `2.4e6,20e6`, and its `--gain` sets the same gain on both); each reading is in the dBFS of the receiver that took it (levels aren't calibrated between them). The GUI's second receiver doesn't use the controller: its `ReceiverDsp` runs its own `_ReceiverChain` (the main window's channel filter and demodulators) on its own device's blocks, and the transmissions it monitors come from the main window's transmitter. Nor does the Scanner tab's Use both receivers: the scan engine tunes the second receiver window step by step and takes the blocks its display loop reads (see Key Modules: `scanner_panel.py`).

## Important Notes

### The display loop
- A 33 ms timer calls `SDRMainWindow._update_display`: `_read_block` takes what arrived since the last frame, and `_process_block` hands that one block to everything that works on the signal (plots, level and squelch, receiver chain and audio, RDS, radio tuner, `SignalTools`, the I/Q recording, S-meter, live decoder, scanner)
- Hardware is polled without waiting (`read_samples(..., timeout=0.0)`); the demo device and a recording playing back are paced to real time by `_Pacer` (a recording never runs ahead)
- `_Pacer.measured` times each frame against the signal time it covers (leaving out the time a recording's read waited for the disk). When the computer can't keep up (`_pacer.overloaded`), frames drop to one block and a full frame is tried once a second to recover; meanwhile the Audio button reads Paused (the status bar says why, at most every 30 s), a running live decoder says it misses part of the signal (not while a Scanner scan runs: `_sync_decoder_skipping`), the Bursts page stops logging and says why, and the waterfall draws the one-block frames' rows as bright as the others without letting them set how bright that is (`_plot_frame` passes `add_line(..., usual=not self._pacer.overloaded)`; the second receiver does too). A recording playing back loses nothing by waiting, so its frames don't drop to one block: they still take what real time owes at 1x (or at a slower speed chosen), at most 50 ms of it a frame (`_Pacer.paced_request`), so it plays at that pace where the computer can, else as fast as it manages (its sound follows the pace it really plays at, see A recording's sound, and pauses only below half of real time, at 2x and 4x as at 1x; at 0.5x only below half of 0.5x: `_realtime` judges a speed below 1x at that speed), and the decoder, which hears all of it, doesn't say it misses part (`_samples_skipped`); nor does the Bursts page pause (`_bursts_frame` pauses only for a device), and Paused's hint gives no advice to lower the sample rate, which a recording can't change (`_realtime_hint`). An I/Q recording still gets every sample (every queued hardware transfer, and the demo's backlog through `_read_demo`; only a disk a second behind loses blocks, see Never block the GUI thread), and what a source skipped (`dropped_samples`) is reported as lost
- New per-frame work goes in `_process_block`, does nothing while its view is hidden or its feature is off, and stays small (measured on a 4-CPU computer, on noise and on the demo's stations, a live decoder takes about 0.3-2.5 ms of the 33 ms at 2.4 MS/s, ADS-B the most; below 2.5 MS/s ADS-B takes about 5 ms in a busy sky, its budget capping any input at about 7-8 ms; a HackRF delivers up to 20 MS/s). Count time in samples where you can, as `scan_engine.py` does, so tests can drive it block by block
- At 20 MS/s a frame holds about 670,000 samples, so keep each part's cost bounded: filter down to the channel first and compute only the outputs kept (the receiver's `_FirDecimator` takes one dot product per kept output wherever that is cheaper than filtering every sample by FFT); reuse the receiver's channel rather than filtering the full-rate block again (the Decoder's RDS takes it through `RDSLiveDecoder.process_channel`, Identify through `receiver_channel_band`); cap a long frame's work (the plots analyze at most `_PLOT_MAX_SAMPLES`, in evenly spread segments); give work that grows with what is received a budget per second of signal (ADS-B's Mode S fit below 2.5 MS/s: `ModeSDemodulator.FITS_PER_S`, `SEARCHES_PER_S`; beyond it the clearest replies are read first); go through a large block in cache-sized pieces (Remove DC spike and Balance I/Q). `tests/test_final_perf.py` (and `tests/test_adsb_bounded_cost.py` for ADS-B) pins these by counting the work
- Nothing else takes samples from the main window's device: the scanner, decoders and signal tools get the loop's blocks (the scanner's host only discards transfers queued before a retune, as `_retune_lo` does)
- Measurements don't depend on the plots' FFT size, window or zoom: LEVEL and the squelch use the channel's own power, the noise floor (Auto squelch, the S-meter's SNR) a fixed 2048-point spectrum (`_power_spectrum_dbfs`)
- The plots' hover readings (`plot_readout.py`) judge the averaged spectrum against the noise measured on that same line, so plain noise reads "noise" at any FFT size; a pixel that holds many bins (about 33 at 32768 points on a 1000 px plot) still needs a carrier about 10 dB over the noise in a bin before it reads as a signal every time (less once zoomed in, or at a smaller FFT size). The zoom changes only what Range > Auto and Color Levels > Auto fit, never a reading: the hover, the measurement box's Peak and the SNRs judge against the whole span's noise

### Tuning: the VFO inside the span
- The LO (`_lo_hz`, the device's center frequency) is the middle of the plots; the tuned frequency (the VFO) can sit anywhere in the span. The receiver chain, decoders and S-meter work at `_vfo_offset_hz()`
- Tune through `set_frequency` / `_tune_to`, never the device's `set_frequency`. They move only the VFO while the channel fits the inner 80% of the span (`_USABLE_SPAN_FRACTION`) and retune the LO otherwise (always, with Radio > Keep Tuned Frequency Centered), to where `_lo_for` puts it: on the tuned frequency, except below half the sample rate, where it goes to half the sample rate so the span starts at 0 Hz (below about a tenth of the rate, only as high as keeps the channel in the usable span, so the span starts a little below 0 Hz). `_tune_to(recenter=True)` puts the LO exactly on the frequency (the Scanner's steps and the transmit path rely on it)
- A frequency out of the device's range, outside a recording that is playing (`_lock_lo`), asked for while transmitting, or outside the usable span while an I/Q recording has samples is refused, with the reason in the status bar and everything left on the frequency tuned (`_refuse_tuning`: red, but amber while transmitting, as every "not while transmitting" notice is). A take holds one center frequency, as it holds one sample rate and one device: while it has samples, tuning inside the span moves only the VFO (Keep Tuned Frequency Centered too), and Device > Connect..., Disconnect and Use Demo Device ask before they end it (`confirm_stop_recordings` in `device_controls.py`)
- After a hardware retune, `_retune_lo` drops the samples taken on the old frequency. Recordings are labeled with the LO (their center frequency), not the tuned frequency; a SigMF take's description names the tuned frequency and mode (`_take_details`)

### Never block the GUI thread
- Long jobs run in workers with progress and Cancel: `file_jobs.run_job(parent, title, label, work)` runs `work(report)` in a `QThread`, shows a progress dialog after 400 ms, holds all keyboard and mouse input except the dialog's own (Cancel) meanwhile (the spectrum keeps running) and returns a `JobResult`. Convert, save and decode recordings, Find Signals in Recording, the Decoder's Export and Transmit Text > Save use it; a cancelled or failed write leaves no partial file. While a job runs, `file_jobs.busy_with()` gives its title, and the Decoder's and the audio's hints name that job, not the device or the sample rate, as what makes the display loop skip, also for as long after it as that skipping is still measured (`_busy_job_now`, `_JOB_SKIP_S`), then in the past tense ("Decode Recording kept this computer busy, ..."; `busy_with()` no longer names it). So title a job with its command's name ("Decode Recording", "Save Text Signal"): the hints read "Save Text Signal keeps this computer busy, so audio is paused meanwhile." (`TestEveryJobTitleReadsInTheHints` in `tests/test_final_finish.py` checks every `run_job` title)
- The transmitter streams from its own thread, polled by a timer; Identify and burst analysis run in a thread pool, and the bursts worker spends at most a quarter of the signal's time taking bursts apart (`ANALYSIS_SHARE`, timed in its own processor time; beyond it, a burst is listed without its analysis)
- Don't make the display loop wait for a thread that may not get a processor on a busy computer: the plots hand half of a large frame's FFTs to a helper thread, and the loop does that half itself when the helper hasn't started on it
- The I/Q recording is written by the take's own writer thread: `_capture` only copies each block into `_SampleStore.queue()` (a `BackgroundWriter` that holds up to a second of signal, 200 MB at most: `_capture_queue_bytes`), so a frame never waits for the disk. A block the queue has no room for (a disk that can't keep up) is left out of the take, counted and said as samples a device drops are ("The recording has gaps: ..."). A write that failed on the writer thread is raised once, on the GUI thread, by the next `queue()` or by `_take_write_failed()` from the status timer, and stops the recording saying why. Stop first waits until the queue is written (`_take_write_failed(wait=True)`), so the take is whole before it is offered for saving or saved automatically; the store's readers (`samples()`, iterating, saving) wait for the queue too, and the free-space check counts what is still queued, so read a take only through its store. The second receiver's recording writes the same way (`_record_writer`)
- The second receiver's frame (`_frame` -> `_feed`) runs in three parts: the GUI thread's (`_frame` reads; `_frame_job` records, gives the real-time hint and decides whether the plots want the frame), `FrameWork` on its `FramePipeline` worker (channel filter, demodulation, level and squelch, tone squelch, the live decoder, the plots' spectrum) and `_present` on the GUI thread a frame later (paint and play, say a clipping warning, and hand the frame's decoded messages and the line being received to the Decoder tab). `_feed` collects the frame in flight before it submits the next, waiting while that one still runs: the worker is never more than a frame behind, and a slow worker slows the second receiver's frames (its pacer sees them) rather than piling up work. While a frame is in flight, what the DSP and the analyzer keep belongs to the worker: call `_settle_frames()` (it presents the frame in flight) before anything resets or reconfigures them (a new sample rate or FFT size, a retune, Stop); the settings a user changes (mode, filter, tuning, squelch level, the listening `options`, the tone squelch's one `tone_squelch` value, the shared de-emphasis, blend and tail elimination) are plain values the next frame reads. The Decoder tab's Clear says it is clearing first (`DecoderPanel.clearing`, before any row goes), and the Second Receiver presents its frame in flight then, so that frame's messages go with the rest. Put new per-frame work in the part for its thread. Both windows share one GUI thread, and the worker competes with it for Python's GIL: it takes part of the second receiver's work off the GUI thread, not all of it
- Widgets are touched only from the GUI thread: a worker's job (`FrameWork`) and a writer's write function never touch Qt; they hand their results back to it

### Broadcast FM stereo: what hears stereo, what hears mono
- Only what you hear and a stereo Record Audio take get left and right. `_ReceiverChain.demodulate()` returns the mono program, (L+R)/2, in every mode (the same samples as without stereo); with the chain's `stereo` set (the window sets it from Radio > Audio > Stereo and who listens, below), on a broadcast deviation and through a filter `StereoPath.usable` accepts, `stereo_audio` holds the block's `(n, 2)` left and right whenever there is stereo to play (None otherwise). `_route_audio` gives `heard` (left/right, else the mono audio) to the speaker, its fade-out and the Record Audio take. Everything else keeps the mono audio or the I/Q: the squelch, LEVEL and the S-meter (the channel's own power), the tone squelch and SSTV (`pre_nr_audio`; DCS reads `fm_raw_audio`), the clipping warning, RDS and the decoders. The Second Receiver window plays stereo the same way through its own chain (its own Stereo switch: `ReceiverDsp.stereo`; `Frame.audio` is `(n, 2)` while stereo plays)
- Stereo is decoded only for someone: for the speaker (and its fade-out), a two-channel take, and the STEREO badge and the radio tuner's lamp while a broadcast station is above the squelch, but not while nobody can hear this receiver (`_audio_held()`: a computer that can't keep up, or a recording playing below half of real time, a quarter of it at 0.5x; the Second Receiver's Listen playing only that receiver) unless a stereo take records it, and never for SSTV, a tone check or a mono take alone. A recording at 0.5x, 2x or 4x on a computer that keeps up is heard, so its stereo is decoded. Through a filter too narrow for it the badge says so without decoding anything. The Second Receiver decodes stereo by the same rule (`ReceiverDsp._audio`: for what plays or fades out, and for its lamp while someone listens)
- `StereoPath.sync` copies the chain's own audio stages (`_build_audio_stages` and their `_phase`), its resampler's `_time` and its DC blocker's state; left and right line up only while those copies match, so a change to those classes must keep them in step. Another de-emphasis swaps those stages mid-stream: `deemphasis.carry_state` starts each new `_FirDecimator` where the old one is (its `_history`, `_phase` and `_taps`) and `StageCrossfade` plays the old into the new over 10 ms, in the chain and, from the same sample, in `StereoPath.change_deemphasis`, so a change to `_FirDecimator` must keep `carry_state` in step too. The notch and low cut leave broadcast FM untouched (`_listen` returns its audio as it came): if they ever filter it, the difference signal needs the same filter, in `StereoPath.process` before its noise reduction
- The speaker opens in two channels and plays mono on both, so stereo coming and going never reopens it (no gap, no click); `AudioJoin`, the sink, `AudioTake` and the time-stretch take mono or `(n, 2)` blocks. A take keeps the channels it started with: two when it starts on broadcast FM with Stereo on (mono audio then goes on both channels), else one

### One audio setting for both receivers
- Radio > Audio's De-emphasis (75 or 50 µs), Stereo Blend (Less, Normal, More) and Squelch Tail Elimination are the main window's, for both receivers: the main window keeps them (`_audio_options.deemphasis_s`, `_audio_options.stereo_blend`, `_tail_elimination`; saved as `audio/deemphasis`, `audio/stereo_blend`, `audio/tail_elimination`), and the Second Receiver takes them up when it opens and whenever one changes (`SecondReceiverWindow.follow_main_audio`, reached through `_second_rx_follows_audio` from each setter). They are plain values its DSP worker reads at its next block (its chain through `ReceiverDsp.options`, its CTCSS detector's burst switch), so a change reaches it without a click. Give a new setting meant for both receivers the same path, and end its menu item's tip "The Second Receiver uses it too." as these do. They are one choice for the whole app, not one per bookmark or band-plan region (someone listening across a border switches de-emphasis by hand; radios often set tail elimination per channel)
- Each window keeps its own Stereo switch (Radio > Audio > Stereo is the main window's; the Second Receiver's is in its Squelch and audio group), Notch, Low cut, Tone squelch and its Reverse, decoder and squelch level; the Second Receiver's Listen chooses which receiver the speakers play

### The tone squelch: one verdict per signal
- Both receivers reset their `ToneSquelch` when the squelch opens on a signal (the main window in `_route_audio`, by `_tone_gate_open`; the Second Receiver in `ReceiverDsp.process`, when `SquelchGate.update` says "opened"), on another channel, and whenever demodulation stops (the squelch closed after its hang, or nothing left that needs the audio). Record Audio, SSTV and a tone check keep the receiver demodulating with the squelch closed: without the reset the noise between transmissions read as "no tone", and a reverse tone squelch played the station it mutes for the first half second of each transmission. A new path that demodulates while the squelch is closed must keep this
- A reverse tone squelch opens only once it is sure the tone or code isn't there (`REVERSE_DECIDE_S`, 0.55 s of audio) and only on a carrier that is really there: both windows pass `process(audio, carrier=gate.is_open and not gate.hanging)`, since the noise the squelch's hang lets through after a carrier drops is no station without the tone; a station it is already playing goes on playing through the hang. What it holds silent reads TONE on the LEVEL lamp with the reverse reason (state "reverse"), in both windows, decided for the same frame as the sound
- The CTCSS reverse burst and the DCS turn-off code let a held tone or code go within about 100 ms, before the squelch tail; Squelch Tail Elimination (`ToneSquelch.tail_elimination`) switches the burst only. Scan Bookmarks judges a channel by the same `ToneSquelch` (reversed for a TSQL-R or DTCS-R bookmark), so it hears a channel as the speaker would
- Not done, and why: a muted station keying up within the squelch's 0.3 s hang after another station stops plays until its tone or code is found (about half a second), as does the station a reverse tone squelch mutes with the squelch off; telling a key-up from a fade would need a carrier-drop detector in both receivers (judging every carrier that comes back within the hang afresh would mute the stations it should play after each deep fade). Voice pitched near a station's tone can fake a reverse burst now and then (the station is cut for about 0.8 s: that is what the switch is for), a burst right after the last syllable is missed 13-32 % of the time (more often the more gently the radio filters its voice; the tail is then heard as before), and the "55 Hz tail tone" some cheap radios send isn't looked for

### A recording's sound at every speed
- Each block's speaker audio goes through `SDRMainWindow._speak(audio, last=False)`; the only other write to the speaker is `_between_blocks` (below). While a recording plays it passes through `_playback_sound` (`PlaybackSound`, Qt-free): `note(seconds, now, speed)` every frame, squelch open or not, measures the pace the recording really plays at (a frame later than `STALL_S` counts as a stall), and `play()` time-stretches the audio to that pace with its pitch kept (`dsp/time_stretch.py`), keeping the speaker at its cushion or a quarter above the longest recent wait between frames (`WAIT_MARGIN`), and never giving it more than AudioSink's own buffer (`MOST_HELD_S`). At 1x, while the recording keeps up, it returns the same array. A block longer than the speaker holds (a slow recording: 8 kHz audio is half a second a block) is given out as it plays, frame by frame, from `_between_blocks` (`more()`), which also feeds the frames between such a recording's blocks at other speeds
- The end (Loop off): once the device has `finished`, `_speak` passes `end=True` and what the stretch holds plays out at the speed chosen; the playback's tick pauses (ENDED) only when `PlaybackSound.rest_s` is 0. Loop turned on as the end plays goes straight on (`FilePlaybackDevice.play_on`, the sound continuing)
- Only the speaker's sound is stretched: Record Audio, SSTV, the decoders, the tone squelch and LEVEL get the recording's own audio at its own pace (10 s of recording make 10 s of WAV at any speed). `_realtime()` judges a speed below 1x at that speed, so a recording's audio pauses (`_audio_held()`) only below half of real time, at 2x and 4x as at 1x (at 0.5x, below a quarter of it): a speed other than 1x mutes nothing by itself. A sound nobody hears any more (Audio off, the Second Receiver's Listen on This receiver) ends at once, faded
- Not done: 4x is for finding where something is said (speech is hard to follow at it, and `speed_note` says so); music at 0.5x can sound phasey (each 25 ms piece plays about twice); a computer about five times too slow for the speed (or a slow one whose frames vary by 20 % or more) and a stall of the window still break the sound up now and then. None of it was heard on a sound card: `PlaybackSound` was judged against a model of AudioSink and in the window offscreen

### One-channel files become I/Q
- `dsp/real_iq.py` turns a one-channel WAV file into I/Q for every reader (`IQPlayer`, `FormatDetector`, `FormatConverter`, the file jobs, `sdr-scan`): the analytic signal at half the file's rate, centered on a quarter of it. So a reader's `sample_rate`, `total_samples`, `position` and `duration_seconds` are the I/Q's (half the file's samples), and its `center_frequency` is a quarter of the file's own rate unless a sidecar or the caller places it elsewhere (an IF at 10.7 MHz). Where the file's own rate or samples are needed, use `IqFileOptions.frame_rate` (or `FormatInfo.metadata["wav_frame_rate"]`) and `recording.wav_frames`; Import Options asks a one-channel file whose header gives no rate for its own rate (prefilled from the file name) and stores half of it as the I/Q rate
- Whether such a file is a receiver's sound is one rule, `real_iq.is_audio` (200 kHz or less, at its own frequencies: `IqFileOptions.audio`), which Open, Recording Info, Convert and Decode Recording and `sdr-scan decode` all follow. Every one-channel file is tuned over its whole span (`usable_fraction`), down to 1 Hz for one from 0 Hz (`_LOWEST_PLAYBACK_HZ`); audio opens in USB from 0 Hz at its own pitch while Radio > Choose Mode From Band Plan is on, its status line naming the band heard ("so its sound from 0.2–2.9 kHz plays at its own pitch"). File > Decode Recording decodes its sound as a receiver's audio for APRS, POCSAG and FLEX (the FM discriminator's audio, not a speaker's) and ACARS (`decodes_as_audio`, `create_live_decoder(..., audio=True)`), Morse at the tone's pitch from its I/Q (type the pitch, "700 Hz", in the dialog's Frequency box), and doesn't offer ADS-B (its rate is far too low); `sdr-scan decode` does the same, `cw` finding the pitch itself (or `--pitch`)
- Not done: the Decoder tab's live decoders don't decode an audio recording's sound as it plays (they say to use File > Decode Recording; CW still decodes its tones), SSTV isn't one of Decode Recording's decoders, a file's sound plays only up to under a quarter of its rate (the receiver demodulates the I/Q at half the file's rate: 8 kHz audio to about 1.9 kHz), and its very lowest and highest frequencies are converted less cleanly (in 48 kHz audio a tone's mirror is 54 dB down from 300 Hz up but 20 dB at 150 Hz; it shows at the other edge of the span, never on the signal)

### Recordings' and receivers' messages in the views
- `DecoderPanel.add_message(..., source=, at_s=, when=, receiver=)` decides where a message goes. With `source` (a recording's name) its row reads "ADS-B (file)" and is counted apart, and in the Aircraft and Text views it goes to that recording's own list under "Showing:", never the live one. A recording's list runs on the recording's clock (`when`: SigMF's `core:datetime`, shown in local time; else `at_s`, the time into it, "1:15"), so its aircraft never dim or go (`AircraftTracker(..., ages=False)`)
- File > Decode Recording names a recording with `_decoded_name(path)`: its file name, or, once another file of that name was decoded in this session, as many of its folders as tell it apart ("tuesday/capture.wav"), keyed by its real path and kept for the session (the first file of a name stays "capture.wav"). Use that name wherever the decode's rows, notes and status lines name the file; `recording_decode_started(name, protocol)` starts that protocol's view's list of it over (another protocol's view keeps its list of the file)
- With `receiver` (the Second Receiver's `RECEIVER_MARK`, "2nd RX") the row says "2nd RX · " before the protocol and is counted apart; its aircraft join the live Aircraft list, one row per aircraft (`Aircraft.heard_by`: which receiver heard it and when; a reply both receivers decoded within `AircraftTracker.COPY_S` counts once), and its Morse text is an entry of its own under "Showing:" (`receiver_source(mark)`), the line being received, its speed and Receiving coming from `DecoderPanel.set_receiver_live`. A view holding a recording's or another receiver's list stays as a tab whatever this window decodes, without taking the front, until Clear; Clear empties every list, after `clearing` (see Never block the GUI thread)

### Scan results: fields in a fixed order
- `scan_engine.Found` and `scanner_panel.ScanHit` keep a result's tone squelch as `tone_hz`, `dcs`, `reverse`, in that order, then whose reading it is (`Found.receiver`: `MAIN`, `PARTNER` or None; `ScanHit.receiver`, "main", "second" or "", and `readings`, each receiver's strongest peak in its own dBFS). Keep `reverse` directly after `dcs` (`ScannerPanel._on_found` passes the squelch by position), pass `receiver`, `readings` and anything newer by name (as `_on_found` does), and add a new field at the end, so a field added later can't shift the others
- Saved results (`scanner/results`) come back through `ScanHit.from_dict`: a damaged newer field (reverse, receiver, readings, DCS) is dropped alone and the result kept (a true/false is no level, a list or an object no receiver), while one whose frequency, level or tone isn't a number is dropped whole. A result never says which receiver read it once it becomes a bookmark (a bookmark is a frequency either receiver can tune)

### Export: every decoded message since Clear
- The Decoder's table and Log keep the newest 1,000 messages; each message is also appended, as the row Export writes (`_export_row`, `EXPORT_COLUMNS`), to a `MessageSpool` file in the system's temporary folder, written through, so a row is there whole or not at all. Export (a `run_job`, "Export Decoded Messages") writes the spool's rows as they are, then the table's newer messages: a new column means changing `EXPORT_COLUMNS` and `_export_row` together
- Clear empties the spool, closing the window deletes it (`discard_spool` in `closeEvent`), and a spool a crashed session left is deleted by the next one (`remove_stale_spools`; a spool in use is locked). When the disk fills, the spool keeps what it has and takes no more until Clear: `spool_failed` puts one warning in the status bar (and Error History), and Export says how many messages it saved and why the others are missing (those between the last one spooled and the table's newest 1,000 are lost)

### Settings survive damaged values
- A settings file can hold anything (a hand edit, another version). `GuiSettings` getters give the default, logged once per key, for a value of the wrong type, a NaN or infinite float or an integer beyond 32 bits; saved bookmarks come back through `usable_bookmarks` (an entry that isn't a bookmark is skipped, one without a usable frequency is listed at 0 Hz)
- The getters can't know a key's range, its choices or the shape of JSON stored in it: check those where you read it and fall back to the default, or to the nearest valid value where that is harmless (the end of the tuning range; never the costliest FFT size or a squelch that never opens), and log it. The plots' saved display settings (JSON) show how: `apply_display_settings(settings, defaults=...)` reads each yes/no with `saved_flag` (never `bool()`, which reads "no" as yes) and each number with `saved_number`, and logs each damaged value with what it used instead (`log_damaged_setting` in `spectrum_widget.py`; an average or a history length the menus don't offer gives the nearest one). JSON of another shape than the one saved (a list or a number where an object belongs) is as damaged as JSON that can't be read: give the defaults and log it, as the plots' restores in both windows (`_saved_choices` in `second_receiver.py`) and the Ham ID, QRP and radio-preset restores do. Restore each value on its own (`restore()` in `_restore_audio_settings`, which also brings back the Notch, its frequency, the Low cut, the DCS code and the Reverse switch: an unknown choice reads Off, a notch frequency out of range its box's nearest end, a damaged DCS code is ignored, each logged; Radio > Audio's De-emphasis and Stereo Blend are read with `_saved_choice`, which logs anything but one of its choices and gives the default, 75 µs or Normal): a damaged setting must never stop the others, the app from starting or a window from opening
- Safety settings fall back to the safe side: an unreadable `tx/confirm` asks before transmitting

### Both themes
- Every color comes from the `Palette` in `themes.py` (Catppuccin Mocha dark, Latte light). Tag widgets with `set_role` / `set_tone`; in `paintEvent` read `get_palette()` and drop cached pixmaps on `theme_notifier().theme_changed`. Never hard-code a color
- Check new UI in both themes (View > Theme), at the minimum window size, 1024x640, and at 1366x768 (a laptop screen); the Second Receiver window at its own minimum, 860x560. At 1024 px the status bar keeps 220 px for messages (`_MESSAGE_MIN_WIDTH`): a status-bar chip whose text can grow should give way rather than widen the window, as the decoder and scan chips (`DecoderChip`) do. A message cut short there shows whole just above the status bar while it lasts (`MessageOverflow`, see Keys, menus and messages), in its tone in both themes

### Transmit only through the transmitter
- Everything the GUI sends goes through `StationTx.transmit(TxJob)` -> `Transmitter`, the only GUI code that calls the HackRF's `start_tx`. Send ID Now and Radio > Send Station ID reach it through `StationTx.send_station_id`; Transmit Text and any other job through `SDRMainWindow._transmit_job(TxJob)`
- That path checks the device can transmit (the demo device and RTL-SDR refuse, with the reason), the license class, band segment and protected frequencies for the emission's own mode and occupied bandwidth (CW is allowed in every segment the class holds, FCC 97.305(a)), a callsign for amateur transmissions, and the power limits. It asks before each transmission until "Don't ask again" is ticked (`tx/confirm`; Ask before transmitting in Tools > Preferences turns the question back on), adds the automatic station IDs, shows ON AIR, pauses receiving (half duplex), puts the HackRF back afterwards and ends with the outcome in the status bar
- While on the air the transmit state wins: `_show_tx_state(True)` (called by `StationTx` when a transmission starts, and by `_refresh_state_ui` while `_tx_busy()`) turns Start and Radio > Start Receiving off and dims the plots with "Transmitting - receiving resumes when it ends", or "Transmitting - press Space to receive once it ends" when the receiver was stopped before (it stays stopped: `_tx_resumes_rx()`); `_refresh_state_ui` turns them back on afterwards. Update Start and the plots' state through `_refresh_state_ui`, so a transmission always shows
- A `TxJob`'s source can make its samples as they are read (`read(n)`, `total_samples`), so a long transmission never has to sit in memory
- Don't call `start_tx` / `write_samples` from GUI code, and don't loosen a check to make a test pass: use the fake HackRF backends

### Keys, menus and messages
- `_add_action` makes a menu action the only owner of its shortcut; `tests/test_gui_coherent_window.py` fails on a key bound twice, and `tests/test_final_window.py` on an access letter (`&`) used twice in one menu
- Keys that must leave a focused slider, list or text field alone (Space, Left/Right, `[` `]`, P, M, Home, Page Up/Down) are handled in `keyPressEvent`, not bound as shortcuts; a menu item shows such a key after a tab (`"&Start Receiving\tSpace"`). A window shortcut that a focused widget should keep is handed to it in `SDRMainWindow.event`, which accepts its `ShortcutOverride` (Ctrl+Up/Ctrl+Down: Volume Up/Down, but ten steps in a number field and a row up or down in a list)
- A menu item that changes a control panel setting follows its control: checked as it is, and disabled while it is (`follow()` in `_add_listening_menus`: Radio > Mode, Radio > Squelch, and Radio > Audio's Noise Reduction, Audio AGC, Notch, Low Cut and Reverse Tone Squelch, which follows the Audio group's Reverse). Radio > Audio > Stereo, Stereo Blend, De-emphasis and Squelch Tail Elimination have no control in the panel: they are actions of their own (Stereo Blend and De-emphasis exclusive choices in a submenu, `_add_choice_menu`), saved at once (`audio/stereo`, `audio/stereo_blend`, `audio/deemphasis`, `audio/tail_elimination`)
- List every new key in `help_dialog.py`: a window key in `SHORTCUTS` (F1 checks the table against the real bindings), a key a focused plot handles in `PLOT_KEYS`, and a key a list, field or window handles itself in `PANEL_KEYS` with an id. `tests/test_gui_help_keys.py` presses each `PANEL_KEYS` row on its real widget in a `test_key_<id>` test and fails when a row has none
- A refusal says what and why ("2400.000 MHz is out of range: RTL-SDR tunes 0.5–1766 MHz."). Use `_show_status_message(text, tone, ms)` / `_show_status_error`. A long action ends with its outcome in the status bar, never a stale "Preparing...", and a message that stops being true is replaced or cleared (a refusal by the next good tune, "Recording armed..." once samples arrive)
- A message too long for the status bar (with every chip shown it keeps 220 px at 1024 px; at 1366 px messages over about 70 characters don't fit) also shows whole in a panel just above it for as long as it shows (`MessageOverflow`, the window's `_message_overflow`): starting above the message's first letter, in its tone, wrapped to the window, five lines at most (then "…"; the message label's tooltip and the status history hold all of it), and above the playback strip while a recording plays (`keep_clear_of`). Nothing else moves; a click on it, or Esc in the window (`keyPressEvent`, where Esc still returns the focus to the plots; a focused control that uses Esc, such as the Decoder's list with a message selected, the Bookmarks filter with text in it or the waterfall's measurement, takes the first one), hides it until the next message. It follows `_show_status_message` and `_clear_status_message`, which also make the message the label's accessible description, so never set the message label's text directly. Still put what matters first: the panel covers the bottom of the plots and the right column while it shows. The Second Receiver's status line has one too (it has no status history, so its tooltip doesn't promise one)
- A hint that names its cause (why a live decoder misses part of the signal, why audio is paused) is said once per episode, and again, once, when the cause changes while the status bar still shows the hint and the new cause has held a second (`HintFollower`: `_skip_follow`, `_audio_follow`, `HINT_SETTLE_S`). Blame this computer only while it is overloaded or was within the seconds real time is judged over (`_computer_behind()`), never for an overload from before a new sample rate, device or recording
- Tools > Error History lists problems only. It takes every WARNING (or worse) any logger writes, and the status bar logs what it shows in the "warning" tone or with `_show_status_error` unless you pass `log=False` (a refusal `_show_status_message` shows in "danger", such as a frequency out of range, is not logged): pass it when you logged already (a problem is listed once) and for a notice that is no problem, such as what to do first ("ID not sent: enter your callsign in Ham > Ham ID first."), what the app did as asked (a scan stopped by Space, Open Recording or a new sample rate; "Recording paused", "Recording armed...") or what a feature can't do in the mode chosen (Track Signal in SSB, I/Q or broadcast FM). A part that logs its own problems shows its messages with `log=False` (`WindowScannerHost.scan_message`: the scan logs a step that broke, and a receiver that returns no samples, whichever tab is shown). Warn only about what is in use: a paused decoder doesn't warn that the sample rate is too low for it. List the same problem once: a decoder that can't work at the rate is logged once for the device and once for a recording until the decoder or the rate changes (`_decoder_logged`), though the status bar, the Decoder line and its chip say it at every rebuild. Tests check that a notice stays out with `assertNoLogs(level="WARNING")`
- One action, one message: an action that sets the mode along the way (the band plan, a preset, a bookmark's or the Decoder's Tune to, the Signal tab's Apply Mode, going back when a recording closes) sets it quietly (`_quiet_mode_change`; presets: `_applying_preset`) and says once what it set; the mode change alone would first name the mode's last filter ("AM: 6 kHz"). A message that something said along the way would replace carries it instead: Open Recording in another band leads the band plan's line with "Playing fm8.sigmf-meta (98.9–101.3 MHz) · " (`_listen_by_band_plan(..., lead=)`, `playback.playing_line`), and in the same band puts the decoder's note after the file ("Playing air125.sigmf-data (...) · ACARS decoder off. Click ..."; `_release_note`), an audio file puts how it is heard after the file ("Playing scanner_audio.wav (one channel, 0–0.024 MHz) · Audio: listening in USB from 0 Hz with a 2.7 kHz filter, so its sound from 0.2–2.9 kHz plays at its own pitch ..."; `_hear_as_recorded`), and a speed other than 1x says how it sounds at once (`set_speed`: `speed_note`, "Playing at 2x: the sound keeps its pitch."). A closing message carries what its steps just said rather than replacing it (Close Recording: "Closed aprs2m.sigmf-data. Back to Demo Device (simulated signals). AX.25/APRS decoder off: ..."), and so does a message that would replace one just said: a tune that turned a preset's decoder off leads its own line with "ACARS decoder off · " (`_keeping_release_note`, once), and a scan stopped by a tune from another tab says "Scan stopped · " before the tune's own message (`_scan_frame`): one posted before the tune is done, back in the event loop or at the next frame (`_tune_said`), not one something else posts after it
- Show frequencies with `format_frequency` (`main_window.py`: kHz below 2 MHz, MHz with 3 to 6 decimals above; the Signal tab's `format_mhz` and the Scanner's `_say_freq` name them the same way, while a list's column in MHz stays in MHz) and sizes with `iq_files.format_size`; use American spelling (`TestTheWindowsWords` in `tests/test_final_window.py` checks every text the main window shows) and the controls' own names ("Filter", not "Bandwidth")

### General
- Hardware drivers are optional; graceful degradation if missing
- Closing the window releases and closes the device, discards the temporary recording file and the Decoder's spool, and stops the plots' FFT helper, one step at a time (`quietly()` in `SDRMainWindow.closeEvent`): a step that fails is logged and the next still runs, so the device is closed. The parts' `shutdown()` calls before those steps are not wrapped: a part with background workers must stop them there without raising, and ignore frames after it (`SignalTools.shutdown`)
- Create a widget you hand to a dialog with the dialog as its parent (`QCheckBox("Don't ask again", box)` before `box.setCheckBox(...)`): PyQt's `QMessageBox.setCheckBox` leaves a parentless box to Python, which deletes it while the dialog still holds it, and a restyle (a theme change) then crashes
- mypy ignores errors in `sdr_module.gui.*` and `sdr_module.ham.gui.*`; the rest is type-checked in CI
- Use demo mode for development without physical SDR devices (`--demo`, or Device > Use Demo Device)
